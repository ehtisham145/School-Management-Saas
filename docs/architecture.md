# Architecture

## 1. Shape: modular monolith

One Django backend, one Next.js frontend, one PostgreSQL database. Inside the backend, each feature is a Django app (module) with clear boundaries. No microservices — at 50 schools / 100K accounts a well-built monolith on modest hardware is enough, and it's the only shape one developer can run reliably.

```
                         Internet
                            │
                     ┌──────▼──────┐
                     │    Caddy    │  TLS, gzip, security headers
                     └──┬───────┬──┘
           /api, /ws,   │       │  everything else
           /admin       │       │
              ┌─────────▼─┐   ┌─▼──────────┐
              │  Django   │   │  Next.js   │  marketing (SSG/SSR) + app + PWA
              │  (ASGI)   │   └────────────┘
              │ DRF + WS  │
              └─┬───┬───┬─┘
                │   │   │
     ┌──────────▼┐ ┌▼───▼─────┐   ┌──────────────┐
     │PostgreSQL │ │  Redis   │◄──┤ Celery worker│  PDFs, emails, bulk jobs
     └───────────┘ │cache/queue│  │ Celery beat  │  scheduled jobs
                   │ /channels │  └──────┬───────┘
                   └───────────┘         │
                       OCI Object Storage (files, backups)  ·  SES (email)
```

All of this runs as containers on **one VPS** at launch (see §9).

## 2. Multi-tenancy

**Model:** shared database, shared schema, `school_id` FK on every tenant-owned row. ([ADR-0002](decisions/0002-multi-tenancy-shared-schema.md))

```python
# apps/core/models.py
class TenantModel(models.Model):
    school = models.ForeignKey(
        "tenancy.School", on_delete=models.PROTECT, db_index=True
    )
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True
```

**How the current school is resolved:**
1. User logs in → session stores `active_membership_id`.
2. `TenantMiddleware` loads the membership, sets `request.school` and `request.role`.
3. Users with several memberships switch via `POST /api/auth/switch-school/` (validated server-side).
4. **Never** trust a school id from the URL, header or body for scoping.

**How isolation is enforced (layers):**
1. Selectors take `school` as their first argument: `list_students(school, *, section=None)`.
2. Base DRF viewset `TenantScopedViewSet` builds every queryset from `request.school`; objects outside it return **404** (not 403, to avoid leaking existence).
3. Serializers validate that every FK in input (section, subject, student) belongs to `request.school`.
4. Unique constraints are per school: `UniqueConstraint(fields=["school", "admission_no"])`.
5. Test fixture creates two schools; every endpoint has a test that School B's user gets 404 on School A's objects.
6. **Hardening phase:** PostgreSQL Row-Level Security using `SET app.current_school` per request as a safety net.

**Super Admin** is not a tenant member. It is a platform flag on the user (`is_platform_admin`) and uses separate `/api/platform/...` endpoints. Cross-school access is only through those endpoints and is always audit-logged.

## 3. Authentication

| Who | Method | Notes |
|---|---|---|
| Parent | Email + one-time code (6 digits) | Code hashed in DB, 10-min expiry, max 5 attempts, rate-limited per email + IP |
| Student | Username + password | Username generated by system, globally unique, school-prefixed: `alnoor.s1024`. School admin resets passwords |
| Parent without email | Username + password (fallback) | Issued by school admin |
| Teacher / Principal / Admin | Email + password + **TOTP 2FA** | 2FA mandatory for School Admin; optional or mandatory for others per school setting |
| Super Admin | Email + password + **TOTP 2FA mandatory** | |

- Sessions: Django DB/Redis sessions, cookie `HttpOnly; Secure; SameSite=Lax`, 12h idle timeout for staff, longer for parents on PWA.
- Passwords: Argon2, Django password validators, `django-axes` lockout after repeated failures.
- CSRF: Django CSRF cookie + `X-CSRFToken` header from the Next.js client.
- Same origin (`https://app.<domain>`): Caddy routes `/api` and `/ws` to Django, so there is no CORS. In development the Next.js rewrite does the same job, so `dev.py` lists port 3000 in `CSRF_TRUSTED_ORIGINS`.
- A user with one active membership has it activated automatically at login. Users with several choose one through `POST /api/auth/switch-school/`.
- `GET /api/auth/me/` returns the user, memberships and active membership. The frontend uses it to restore the session after a refresh.
- Public sign-in endpoints skip session authentication, so an old session or a missing CSRF cookie in the browser can't block a login. Endpoints for signed-in users still require CSRF.
- Email-code login still requires TOTP if the user has a confirmed device.
- Super Admins and active School Admins must use TOTP. Until they set it up, login returns `requires_2fa_setup: true` and `HasPolicy` answers 403 `2fa_setup_required`.
- `/api/platform/` needs `is_platform_admin` and a session verified with TOTP (`user.is_verified()`), so a password-only Django admin session is refused.
- A new School Admin gets no password: the Super Admin enters their email, and they sign in with an email code, then set up TOTP.
- Demo request phone numbers must be Saudi mobiles and are saved as `+9665XXXXXXXX`. The frontend blocks other characters, and the backend checks again.
- The public Book a demo and Contact forms post to `/api/platform/demo-requests/` and `/api/platform/contact-messages/`. They use no session, are throttled per IP (`leads` scope) and have a honeypot field. The team is emailed at `LEADS_EMAIL` and submissions are listed in Django admin.

## 4. Authorization (RBAC)

```
User ──< Membership >── School
          role: SCHOOL_ADMIN | PRINCIPAL | TEACHER | STUDENT | PARENT
          status: active | suspended
```

Two questions are asked for every request:
1. **Can this role do this action?** — a permission matrix in `apps/core/policies.py`, e.g. `can(role, "attendance.mark")`.
2. **Which rows can this role see?** — scoping in selectors:

| Role | Row scope |
|---|---|
| School Admin, Principal | Whole school |
| Teacher | Sections/subjects in their `TeacherAssignment` for the current academic year |
| Student | Own records |
| Parent | Records of children linked via `Guardianship` |

The frontend hides buttons by role for UX only. **The backend is the only authority.**

`TenantScopedViewSet` applies `HasPolicy` by default. Each viewset maps its actions to policies, e.g. `policies = {"list": "members.view", "create": "members.manage"}`. An unmapped action returns 403.

## 5. Core data model (MVP)

```
tenancy:        School, Membership, SchoolSettings
accounts:       User, EmailOTP, (django-otp TOTPDevice)
academics:      AcademicYear, Term, Grade, Section, Subject,
                Enrollment(student, section, year), TeacherAssignment(teacher, section, subject, year),
                Guardianship(parent, student, relation)

homework:       Assignment(section, subject, due_at, files), Submission(student, files, grade)

communication:  Announcement(audience), Conversation, Message

```

Money is stored as `DecimalField(max_digits=12, decimal_places=2)` in SAR. Never floats.

## 6. Background jobs (Celery)

| Job | Trigger |
|---|---|
| Send OTP / notification / quotation emails | On event (queue `emails`) |
| Generate report cards for a section (PDF, zipped) | Teacher/admin action; user is notified when ready |
| Fee receipts, quotation PDFs | On event |
| Daily absence digest to parents | Beat, e.g. 10:00 KSA |
| Fee due reminders | Beat, daily |
| Subscription expiry checks | Beat, daily |
| Clean expired OTPs, sessions | Beat, nightly |
| DB backup → Object Storage (other KSA region) | Cron on host, nightly 02:00 KSA |

Rules: tasks are **idempotent**, take IDs (not model objects), and re-check tenant/permission inside the task. Long work → task → notify user. Never in the request.

## 7. Real-time

- Django Channels WebSocket at `/ws/notifications/`, authenticated by the session cookie.
- Each user joins group `user_<id>`. Conversations join `conv_<id>` after a membership check.
- Flow: service saves `Notification` → `transaction.on_commit` → `channel_layer.group_send` → browser updates badge/list instantly.
- Fallback: if the socket is down, the frontend polls `/api/notifications/unread-count/` every 60s.
- Web Push (PWA, Phase 1.5) is sent from Celery for users who aren't online.

## 8. Files, i18n and dates

- **Files:** upload through API → validate type (allow-list) and size (e.g. 20 MB) → store in **private** bucket under `school/<id>/...` → download via short-lived presigned URL after a permission check. Original filenames are never used as storage keys.
- **i18n:** `next-intl` with `/ar/...` and `/en/...` routes; `<html dir="rtl" lang="ar">` for Arabic. Backend stores translatable *data* fields (e.g. subject name) as `name_en` / `name_ar`. ([ADR-0006](decisions/0006-bilingual-arabic-english-rtl.md))
- **Dates:** DB stores Gregorian `date`/`timestamptz` (UTC). Display in Asia/Riyadh time; Hijri via `Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura')` on the frontend and `hijridate` (Umm al-Qura) in Python for PDFs. ([ADR-0005](decisions/0005-dates-gregorian-storage-hijri-display.md))

## 9. Deployment

```
OCI Riyadh — 1 × Ampere A1 VM (2 OCPU / 12 GB, Ubuntu 24.04)
docker-compose.prod.yml:
  caddy        :80/:443
  frontend     next start
  backend      gunicorn config.asgi -k uvicorn_worker.UvicornWorker   (HTTP + WebSocket)
  worker       celery -A config worker -Q default,emails,pdf
  beat         celery -A config beat
  postgres     17, volume on block storage
  redis        7, AOF on
Host cron:     nightly pg_dump → encrypted → OCI Object Storage (Jeddah) ; weekly VM boot-volume backup
```

**CI/CD (GitHub Actions):**
1. On PR: `ruff`, `pytest` (with Postgres service), `eslint`, `tsc`, `next build`.
2. On merge to `main`: build **arm64** images (buildx) → push to GHCR → SSH to VM → `docker compose pull && docker compose up -d` → `migrate` → health check.
3. Environments: `staging` (same VM, separate compose project + DB, at first) and `production`. Deploys outside 07:00–14:00 KSA.

Secrets live in a `.env` on the VM (chmod 600) and in GitHub Actions secrets, never in git.

Local development does **not** use the production compose file. Both machines run fully native (no Docker, no Redis); the settings switch to in-memory fallbacks when `REDIS_URL` is unset. See [development.md](development.md) and [ADR-0009](decisions/0009-local-development-fully-native.md).

**Inside every backend app:**

```
apps/attendance/
├── models.py
├── selectors.py      reads — always take `school` first
├── services.py       writes / business rules — transactions, audit, notifications
├── policies.py       optional, module-specific permission rules
├── api/              serializers.py, views.py, urls.py   (thin: validate → call service → serialize)
├── tasks.py          Celery tasks
└── tests/            test_services.py, test_api.py, test_isolation.py
```

Practices:
- Views stay thin, services own logic. A module may call another module's **services/selectors**, never its models directly.
- Every API response is paginated; list endpoints use `select_related`/`prefetch_related` (watch for N+1 queries).
- API errors use one envelope `{ "error": { "code", "message", "fields" } }`, with messages translatable.
- Migrations reviewed by hand; no destructive migrations during school hours.

## 11. Scaling path

| Stage | Load | What to do |
|---|---|---|
| **~1K–4K accounts** (launch, 1–2 schools) | Tiny | Everything on one A1 VM. Focus on correctness, backups, monitoring. |
| **~10K–20K** (5–10 schools) | Moderate peaks at 07:30 | Add indexes from slow-query log; cache dashboards in Redis; move Postgres to its own VM or OCI Database for PostgreSQL; Postgres RLS on; staging on a separate VM; external log aggregation. |
| **~100K+** (50+ schools) | Real peaks | 2+ app VMs behind OCI Load Balancer; managed Postgres + read replica for reports; dedicated Redis; Celery workers scaled per queue; CDN for static assets; Meilisearch if search is slow. Big customers can get a dedicated DB/schema. **Still a monolith.** |

Signals to move to the next stage: p95 API latency > 500 ms in school hours, CPU > 70% sustained, DB connections near limit, or a customer contract requiring stronger isolation.
